Avant de télécharger

Quel système et quels outils préparer ?

Choisis ton chemin avant de lancer un script. Le logiciel OpenClaw propose plusieurs méthodes ; ce kit indépendant ne les automatise pas toutes. Lis le GUIDE.md et les réserves ci-dessous.

Le script du kit : macOS ou Linux, dans un terminal Bash

scripts/install.sh vérifie macOS ou Linux et la présence de curl, puis lance l’installateur officiel. Lis le script avant de l’exécuter ; sur un VPS, travaille sur le serveur via SSH, avec un compte dédié.

Pour le chemin classique utilisant Node.js, la documentation indique Node.js 24.16+ dans la branche 24, ou 26.1+ dans la branche 26. Vérifie ta version avec node -v si Node est déjà installé ; l’installateur officiel peut le provisionner s’il manque. Docker n’est pas obligatoire.

Windows : méthode officielle native ou terminal Linux dans WSL2

Le kit fournit un script Bash, pas un installateur PowerShell. Si tu choisis WSL2, les commandes Bash se lancent dans le terminal Linux, pas dans PowerShell.

OpenClaw propose aussi des applications Windows et un installateur PowerShell : suis la documentation Windows officielle pour choisir et préparer ta méthode. Ces parcours natifs ne sont pas fournis par le script du kit.

Option Docker : Compose v2, stockage et mémoire selon l’usage

Prévois Docker Engine ou Docker Desktop, avec Docker Compose v2. Vérifie docker compose version et que le moteur Docker est démarré. Garde de l’espace disque pour les images, les journaux et les sauvegardes.

La documentation demande au moins 6 Go de mémoire pour la construction locale d’une image depuis les sources. Le Compose du kit utilise par défaut une image officielle préconstruite : il évite cette construction, mais ne garantit pas une consommation mémoire fixe à l’exécution.

Les prérequis du guide ont été alignés sur cette page ; ils ne sont pas une garantie de dimensionnement. Les outils activés, le navigateur, les autres services et un éventuel modèle local changent les besoins : vérifie ton usage avant de choisir une offre d’hébergement.

Comment vérifier le ZIP téléchargé avant de l’ouvrir ?

Ouvre notre liste des empreintes SHA-256. Depuis le dossier contenant kit-openclaw.zip, lance uniquement la commande correspondant à ton système ; elle lit le fichier sans l’exécuter :

  • macOS : shasum -a 256 kit-openclaw.zip
  • Linux (GNU Coreutils) : sha256sum kit-openclaw.zip
  • Windows PowerShell : Get-FileHash -Algorithm SHA256 kit-openclaw.zip

Compare les 64 caractères du résultat à la ligne kit-openclaw.zip du manifeste, sans tenir compte des majuscules/minuscules. Si le navigateur a renommé le fichier, adapte son nom dans la commande.

En cas de différence, ne lance aucun script. Retélécharge le ZIP et consulte à nouveau le manifeste : une ancienne version peut avoir une empreinte différente. Si l’écart persiste, signale-le au support.

Ce contrôle détecte une différence avec l’archive publiée ; ce n’est pas une signature ni une garantie d’innocuité. Le manifeste et le ZIP viennent du même site : il ne protège pas contre une compromission des deux. Lis toujours les fichiers avant exécution.

Références : SHA-256 avec GNU Coreutils et Get-FileHash de Microsoft.

Dépannage OpenClaw

Installé, mais inaccessible ? Commence ici

Identifie le blocage avant de relancer une installation. Choisis les commandes de ta méthode : installation classique ou Docker. Exécute-les dans ton terminal, pas dans une conversation avec l’agent.

La passerelle ne semble pas démarrée

Installation classique : sur la machine où OpenClaw est installé, lance openclaw gateway status. Consulte ensuite openclaw logs --follow pour repérer une erreur répétée ; Ctrl+C quitte la lecture des journaux.

Avec Docker : dans le dossier du kit contenant docker-compose.yml, lance docker compose ps --all, puis docker compose logs --tail 50 openclaw-gateway. Le premier affiche aussi les conteneurs arrêtés ; le second limite la lecture aux dernières lignes. Si le kit est sur un VPS, ces commandes se lancent sur le serveur via SSH.

Ne supprime pas tes dossiers de données ou tes sauvegardes pour tenter de réparer. Note le message exact et consulte le guide du kit avant toute modification.

Le tableau de bord du VPS ne s’ouvre pas sur mon ordinateur

127.0.0.1 désigne la machine sur laquelle tu ouvres le navigateur, pas ton VPS. Le kit Docker garde volontairement le port accessible seulement en local sur le serveur.

Avec le port par défaut, ouvre un tunnel depuis ton ordinateur : ssh -N -L 18789:127.0.0.1:18789 utilisateur@votre-serveur. Remplace utilisateur@votre-serveur par ton accès SSH, laisse ce terminal ouvert, puis ouvre http://127.0.0.1:18789 dans ton navigateur.

Si tu as changé OPENCLAW_GATEWAY_PORT dans le kit Docker, adapte le dernier port du tunnel au port publié sur le serveur. Ne publie pas le port de la passerelle sur Internet pour contourner le problème.

La page s’ouvre, mais affiche « unauthorized » ou « pairing required »

La page accessible ne prouve pas que ton navigateur est autorisé. Vérifie le jeton de cette installation, sans le confondre avec la clé API du modèle. Avec Docker et une passerelle démarrée, retrouve le lien avec docker compose run --rm openclaw-cli dashboard --no-open, depuis le dossier du kit. Si tu as personnalisé le port Docker, adapte celui du lien au port local de ton tunnel.

Pour une demande d’appairage, suis le dépannage officiel Docker et n’autorise que ton propre navigateur après vérification de la demande. Ne désactive pas l’authentification pour faire disparaître l’erreur.

Besoin d’aide en français ? Contacte notre support avec ton système, ta méthode d’installation et le message exact. Masque les clés API, les jetons et les données personnelles dans les extraits ou captures ; ne joins pas ton fichier .env, un lien contenant un jeton ou une sauvegarde complète.

Sécurité et sauvegardes : rien à supposer

Le kit fournit des fichiers et une méthode, pas une garantie de sécurité ni de récupération. Vérifie les réglages de ta propre installation avant de lui confier des données.

Installation réussie ne veut pas dire sécurité configurée

scripts/install.sh lance l’installateur officiel. Le script du kit ne configure pas ton pare-feu, tes clés SSH ou un accès HTTPS. La checklist securite.md se lit et s’applique séparément, selon ton système ; ne recopie pas une règle réseau sans vérifier ton accès administrateur.

Le Compose fourni publie le port de la passerelle sur 127.0.0.1 de l’hôte. Cela ne remplace pas l’authentification ni le contrôle des outils et des canaux autorisés. Pour un VPS, garde cet accès local et consulte le tunnel SSH expliqué plus haut. Ne publie pas le port sur Internet pour contourner un problème.

Après configuration, lis les résultats de openclaw security audit (installation classique), ou de docker compose run --rm openclaw-cli security audit depuis le dossier du kit Docker, passerelle démarrée. Traite les alertes ; un audit sans alerte ne prouve pas l’absence de risque.

Une sauvegarde ne se programme pas toute seule

scripts/sauvegarde.sh crée une sauvegarde quand tu le lances. Le kit ne programme pas de tâche cron à l’installation : la planification est une étape séparée. Lis le script et le GUIDE.md, fais un premier essai manuel, puis vérifie les journaux et l’apparition d’une archive après l’exécution planifiée.

Par défaut, la destination est ~/Backups/openclaw en installation classique, ou sauvegardes/ dans le dossier du kit en mode Docker. La variable RETENTION_JOURS vaut 14 par défaut : le script supprime les anciennes archives correspondantes selon ce délai après une sauvegarde réussie. Vérifie ce réglage avant de l’utiliser.

Archive vérifiée, copie externe et restauration sont trois étapes différentes

Le script utilise --verify pour contrôler le manifeste et le contenu de l’archive. Ce contrôle ne remplace pas un essai de restauration. Prépare cet essai dans un environnement isolé en suivant la procédure officielle de sauvegarde et restauration, sans écraser ton installation active.

Les archives peuvent contenir des secrets et des conversations. Le script du kit ne chiffre pas les archives et ne copie pas leur contenu sur un autre support. Restreins leur accès, conserve une copie privée sur un autre support et chiffre-la avant un transfert externe. Ne joins jamais une archive complète à une demande d’aide et ne la publie pas sur GitHub.
